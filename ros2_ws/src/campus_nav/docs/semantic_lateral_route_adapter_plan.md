# 基于 OSM 纵向引导与视觉道路边界的动态横向路线适配方案

## 1. 目标与结论

本方案解决以下冲突：

- Campus Nav 使用 OSM 有序路线保证长距离拓扑正确；
- OSM 线只是一条参考几何，可能位于机动车道左侧、中心或边缘；
- Nav2 的中间 waypoint 是具体坐标，高代价只能让路径绕行，不能消除终点对错误横向位置的牵引；
- 固定右偏（例如 5 m）不知道真实道路宽度，也不知道偏移后是道路、人行道、草地还是建筑；
- 图像右侧或车体右侧不能稳定代表道路右侧，尤其当车头朝向路沿、掉头或横穿道路时。

核心结论是将路线约束拆成两个正交问题：

1. **纵向约束**：OSM 有序路线决定走哪条路、沿哪个方向推进；
2. **横向约束**：相机语义分割和深度点云测量道路真实边界，决定横截面上的目标位置。

OSM waypoint 不再是所有中间阶段必须精确压过的点，而是纵向进度锚点。机器人实际追踪的短视距目标由当前观测到的道路右边界动态生成。

## 2. 范围

### 2.1 本阶段实现

- 只对 OSM `highway` 属于机动车道路白名单的路线段启用动态横向适配；
- 从 SAM3 `road` mask 与对齐点云估计道路左右边界；
- 在道路右边界内侧保留安全距离，生成短视距目标；
- 使用路线进度判断中间锚点是否通过，不要求横向命中 OSM 坐标；
- 保留最终目标和离路入口段的精确到达语义；
- 提供完整调试可视化、置信度、降级和安全门控。

机动车道路白名单初始为：

```yaml
[service, residential, unclassified, tertiary, tertiary_link]
```

> 实现状态（2026-09-23）：本节代码已接入 `campus_route_planner`，当前为闭环模式
>（`semantic_lateral_shadow_mode: false`）。除 OSM 相对中心/宽度拟合与路口锁宽外，
> 已增加后向路线的 `ALIGN_ROUTE_HEADING` 原地对齐，以及对图像边缘截断观测的
> `SEEK_RIGHT_EDGE`。固定 OSM 右偏与旧图像列梯度均已关闭。



### 2.2 暂不实现

- OSM A* 中的人行道优先权重；
- 自动选择左侧或右侧人行道；
- 根据路沿高度主动驶上人行道；
- 机动车道不可用时的两阶段重新规划；
- 依赖固定横向偏移量修正整条 OSM 路线。

这些能力应建立在本方案的路线坐标系和动态边界估计之上，而不是另做一套方向定义。

## 3. 为什么必须考虑车辆位姿，但不能用车辆朝向定义道路左右

车辆位姿有两个不同用途，必须严格区分。

### 3.1 车辆位姿必须参与的部分

- 使用图像/点云采集时刻的 TF，将相机点从 `camera` 变换到统一规划坐标系；
- 将机器人位置投影到当前有序路线，得到当前纵向进度；
- 只选择机器人附近和前方可用范围内的观测；
- 检测相机是否实际看到了所需路线窗口；
- 根据速度确定前视距离和目标更新频率。



### 3.2 车辆 yaw 不能参与定义的部分

道路左右不能直接由以下量定义：

- 图像左/右；
- `base_link` 左/右；
- 当前车头 yaw 的法向方向。

原因是车头可能暂时对着路沿、绕障横摆、原地转向或倒车。此时车体右侧与道路右侧不一致。

### 3.3 唯一稳定的道路左右定义

使用 Campus Nav 当前有序路线的行进方向定义道路坐标系。

对路线弧长位置 `s`：

```text
r(s)      路线参考点
t(s)      沿有序路线前进的单位切线
n_right(s) = (t_y, -t_x)
```

任意地图点 `p` 的横向坐标定义为：

```text
d(p) = dot(p - r(s), n_right(s))
```

- `d > 0`：路线行进方向的右侧；
- `d < 0`：路线行进方向的左侧；
- 同一路线反向行驶时 `t` 自动反向，道路右侧也随之正确交换；
- 车辆朝向不会改变该定义。

车辆姿态只影响相机观测如何进入地图坐标系，不影响道路左右的语义。

## 4. 现有系统与数据链

现有语义感知输出：


| 话题                               | 类型                        | 用途                  |
| -------------------------------- | ------------------------- | ------------------- |
| `/semantic/camera1/segmentation` | `sensor_msgs/Image`       | `mono8` 类别 ID       |
| `/semantic/camera1/confidence`   | `sensor_msgs/Image`       | 0..255 置信度          |
| `/semantic/camera1/points`       | `sensor_msgs/PointCloud2` | 与 mask 像素逐点对齐的组织化点云 |
| `/semantic/camera1/label_info`   | `vision_msgs/LabelInfo`   | latched 类别名称映射      |
| `/campus_path`                   | `nav_msgs/Path`           | 原始有序 OSM 路线         |


SAM3 成功推理后同时发布 segmentation、confidence 和 points，三者具有同一采集 stamp。横向适配器必须使用相同 stamp 的数据，不能用最新 mask 配旧点云，也不能把旧观测改盖当前时间戳。

Campus Nav 路线默认在 `campus_map`，Nav2 代价地图在 `map`。计算前必须通过 TF 将路线、机器人和语义点统一到同一坐标系，建议内部统一使用 `map`。禁止假设 `map` 与 `campus_map` 永远重合。

## 5. 总体架构

```text
OSM / Campus Nav
  └─ 原始有序路线 + 每段 highway 类型
                 │
                 ▼
        路线坐标系与纵向进度
                 │
SAM3 mask + confidence + organized cloud
  └─ 同 stamp TF 到 map
                 │
                 ▼
          局部道路边界估计器
                 │
                 ▼
    右边界内缩安全距离的短视距目标
                 │
       障碍/地形/足迹安全校验
                 │
                 ▼
       Nav2 短批次目标或单目标执行
```

推荐在 `campus_nav` 内新增独立模块 `semantic_lateral_adapter.py`，由 `RoutePlanner` 持有并调用：

- `RoutePlanner` 已拥有完整有序路线、当前路线模式、OSM highway 标签和 Nav2 action 生命周期；
- 适配器专注同步语义数据、边界拟合和目标选择；
- 重计算放入单独工作线程，不能阻塞 ROS 订阅和 Campus Nav 的批处理定时器；
- `RoutePlanner` 仍是唯一 Nav2 action owner，避免两个节点同时抢占目标。

不建议第一版创建另一个直接发送 Nav2 action 的节点，否则取消、暂停、最终精确到达和批次抢占会出现双重所有权。

## 6. 路线预处理



### 6.1 保留路线段元数据

当前 RouteGraph 已能保存 `way_id -> highway`。规划结果需要为每个原始路线段保留：

- 起点与终点；
- `way_id`；
- `highway`；
- 是否属于机动车道路白名单；
- 累计弧长区间 `[s0, s1]`。

禁止在路线生成后仅通过“最近 OSM 边”反复猜类型作为最终实现；路口处多条边距离相同，会产生标签跳变。最近边查询只适合原型验证。正式实现应让 A* 重建路径时同步返回所经过的 `way_id`。

### 6.2 建立连续路线弧长参数

将原始折线转换为累计弧长形式：

```text
route = [(p0, s0), (p1, s1), ..., (pn, sn)]
```

提供以下基础操作：

- `project_to_route(p, s_hint)`：在当前进度附近投影，返回 `s, d`；
- `sample_route(s)`：返回 `r(s), t(s), n_right(s)`；
- `highway_at_s(s)`：返回路线在该位置的 OSM 类型；
- `distance_to_junction(s)`：返回到下一个拓扑路口的距离。

投影搜索必须使用上次 `s` 作为窗口提示，不能对自交或平行路线做全局最近点选择，否则机器人可能跳到另一段路线。

### 6.3 路口保护区

路口附近“道路右边界”可能属于另一条支路，单帧 mask 也可能把整个交叉口连成一片。因此在拓扑节点前后设置保护区，例如：

```yaml
junction_guard_before_m: 4.0
junction_guard_after_m: 3.0
```

保护区内：

- 不从全局最右 road 点提取边界；
- 只接受靠近目标支路走廊的 road 点；
- 降低速度；
- 横向目标平滑回到已确认的上一位置或支路内部安全位置。

当前实现采用更保守的第一版：以机动车道路白名单中至少有三个道路臂的 OSM
拓扑节点作为路口，在节点前 `4 m` 锁定最后确认的“道路中心相对 OSM 的横向偏移
+ 道路宽度”。保护区内完全忽略交叉口扩张的 road mask，并让固定偏移沿规划选中的
OSM 支路通过；节点后 `3 m` 之外还需连续三帧新模型相互一致才渐进解锁。OSM
折线切向在节点两侧做短窗平滑，避免固定偏移在转弯顶点因法向突变而跳跃。



## 7. 语义帧同步与坐标变换



### 7.1 同步要求

使用严格同 stamp 的：

- segmentation；
- confidence；
- organized point cloud。

由于感知节点已经同步发布，优先使用 exact time sync，队列深度建议 5。若实测 ROS 序列化造成少量 stamp 差异，再使用 approximate sync，slop 不超过 10 ms。

### 7.2 TF 要求

使用消息采集时刻查询：

```text
map <- cloud.header.frame_id
map <- base_link
map <- campus_map
```

不能使用 `Time()` 的最新 TF 变换历史语义帧。机器人运动时，0.3 s 感知延迟若配最新 TF，会把边界横向投错。

若采集时刻 TF 不可用：

- 丢弃该帧；
- 增加 TF drop 计数；
- 不伪造时间戳；
- 保持上一可靠模型直到超时。



### 7.3 点云过滤

对 road 类像素对应的点执行：

- `confidence >= road_confidence_min`；
- XYZ 有限；
- 距离处于有效范围；
- 点高度接近可行驶地面；
- 路线投影在当前局部搜索窗口内；
- 排除机器人后方过远区域。

为降低计算量，可以按 2x2 或 4x4 像素步长采样；边界附近再做密集采样。目标是让单帧处理稳定低于 50 ms，而不是处理全部 640x360 点。

## 8. 道路边界估计



### 8.1 局部搜索窗口

以机器人当前路线进度 `s_robot` 为基准：

```yaml
boundary_s_near_m: 1.0
boundary_s_far_m: 7.0
boundary_bin_m: 0.5
boundary_lateral_limit_m: 12.0
```

仅使用：

```text
s in [s_robot + boundary_s_near_m, s_robot + boundary_s_far_m]
abs(d) <= boundary_lateral_limit_m
```

这里的“前方”是路线 `s` 增大的方向，不是车头方向。车头朝向路沿时，只要相机观测确实覆盖到该窗口，仍可得到正确边界；若相机没有覆盖，则置信度下降并进入保持/降级状态，而不是把相机右边误认为道路右边。

### 8.2 按纵向分箱

将 road 点按 `s` 分到 0.5 m 左右的纵向箱中。每个箱内计算横向 road 区间。

不能直接使用最小/最大 `d`，因为单个错误像素会把边界拉出数米。建议：

- 左边界：有效 road 点 `d` 的 5% 分位；
- 右边界：有效 road 点 `d` 的 95% 分位；
- 点数不足的箱标记无效；
- 使用中位数绝对偏差剔除离群点。



### 8.3 连通区域选择

交叉路口、停车场和相邻道路会出现多个 road 区域。应选择与当前道路连续的区域，而不是无条件选择最右区域。

种子优先级：

1. 上一时刻已确认的道路横向区间；
2. 机器人投影附近的 road 区间；
3. 与当前 OSM 路线走廊重叠最大的 road 区间。

相邻纵向箱只有在边界变化和中心变化小于阈值时才连接。禁止跨越明显空隙把另一条道路合并进来。

### 8.4 处理标线、斑马线和井盖

这些区域可能导致 road mask 内出现孔洞，但不应改变外边界。处理原则：

- 图像域对 road mask 做小尺度闭运算，只闭合内部小孔；
- 不进行会扩张到人行道的大尺度膨胀；
- 地图域以最大连续横向区间和分位数拟合边界；
- 允许箱内一定比例的非 road 间隙。



### 8.5 边界模型与可信度

对有效箱拟合平滑的 `d_left(s)` 和 `d_right(s)`，可先使用分段线性 + 中值滤波，后续再升级为鲁棒样条。

每个模型输出置信度，至少考虑：

- 有效纵向覆盖长度；
- 每箱点数；
- SAM3 平均置信度；
- 道路宽度合理性；
- 相邻箱边界连续性；
- 与上一模型的一致性；
- TF 和数据年龄。

建议初始道路宽度合理范围：

```yaml
road_width_min_m: 2.5
road_width_max_m: 15.0
```

该范围用于拒绝明显失败，不用于假定真实道路宽度。

### 8.6 相机与雷达/高程的分工

道路边界不应完全依赖相机，但第一版也不需要直接对原始 Livox 点云做复杂的多传感器联合分割。推荐采用“语义提出候选、几何确认与否决”的非对称融合：

- 相机/SAM3 回答“这里看起来属于 road、sidewalk 还是 grass”；
- 雷达、高程图和 terrain layer 回答“这里是否存在高度突变、陡坡、实体障碍或不可跨越路沿”；
- 路线坐标系回答“哪个方向是当前路线的右侧”。

雷达不能替代相机语义：没有高度差的机动车道与人行道、不同颜色铺装、标线边界，在点云几何上可能完全连续。相机也不能替代雷达安全判断：阴影、曝光、积水和相似材质可能造成错误语义边界，而雷达仍能测出真实路沿和障碍。

#### 第一版：复用现有地形结果，不处理原始雷达点云

系统已经存在 elevation/terrain 数据链。第一版只读取现有局部代价地图或 terrain 输出，在相机候选边界附近检查：

- 是否出现连续的高度梯度或 lethal terrain cell；
- 候选目标 footprint 是否跨越不可通行单元；
- 相机估计的右边界外是否存在实体障碍；
- 从当前机器人位置到候选目标是否有连续可行走地面。

这样不增加一套 Livox 点云聚类和地面拟合，只增加查询与一致性判断，复杂度可控。

#### 融合判定表

| 相机语义 | 雷达/高程几何 | 处理 |
|---|---|---|
| 有 road 边界 | 同位置有路沿/高度突变 | 高置信边界，目标保持在边界内侧 |
| 有 road 边界 | 地面连续、没有路沿 | 保留为语义边界；不能因为雷达没看到台阶就否定 |
| 无可靠 road 边界 | 有明确路沿/障碍 | 作为安全边界或否决线，但不擅自认定哪侧是 road |
| 相机与几何明显冲突 | 任一结果不稳定 | 取更保守的内侧边界、降速；持续冲突则停车 |
| 两者都不可靠 | 无 | 进入 `HOLD_LAST`，超时进入 `DEGRADED_STOP` |

这里的“更保守”指离已知障碍、路沿更远且仍位于已确认 road 连通区域内的位置，不是简单选择数值较小或较大的横向坐标。

#### 第二版：原始雷达边界增强（可选）

只有第一版证明相机边界在强光、阴影或遮挡下仍不足时，再增加原始雷达处理：

- 在路线 `s/d` 坐标中对地面点分箱；
- 估计横向高度剖面、坡度和粗糙度；
- 检测连续路沿候选，而不是对整帧点云做通用聚类；
- 将几何候选与相机边界按位置、方向和时间关联；
- 对非重复扫描的 Livox 点云做短时累积，并使用车辆采集时刻位姿补偿运动。

原始雷达增强仍只应输出“几何边界/置信度”，不应单独决定道路语义。

## 9. 动态目标生成



### 9.1 目标前视距离

目标弧长：

```text
s_target = s_robot + lookahead(v)
```

初始可采用：

```text
lookahead(v) = clamp(3.0 + 1.5 * abs(v), 3.0, 6.0) m
```

前视距离必须小于当前可靠边界覆盖范围，不能为尚未观测的远处路线生成虚假偏移目标。

### 9.2 右侧目标

在 `s_target` 处：

```text
d_target = d_right(s_target) - margin_inside
```

安全内缩量应包含：

```text
margin_inside = 机器人半宽 + 路缘安全余量 + 边界不确定度余量
```

当前 footprint 横向半宽约 0.25 m，可从以下初值开始：

```yaml
curb_clearance_m: 0.35
boundary_uncertainty_margin_m: 0.15
```

因此典型内缩约 0.75 m，而不是固定从 OSM 线偏 5 m。

目标必须限制在：

```text
d_left + margin_inside <= d_target <= d_right - margin_inside
```

如果道路宽度不足以容纳 footprint 和双侧余量，该箱不可用。

### 9.3 地图目标坐标

```text
p_target = r(s_target) + d_target * n_right(s_target)
```

目标朝向取路线切线 `t(s_target)`，不取机器人当前 yaw，也不取相机朝向。

### 9.4 障碍与地形否决

语义目标不是安全通行证明。发送前必须用局部 costmap/terrain layer 做 footprint 检查：

- footprint 内存在 lethal/inscribed obstacle：拒绝；
- 地形层判断为不可跨越路沿或陡坡：拒绝；
- 目标周围无足够空间：沿横向向道路内部逐步回退；
- 全部候选均失败：保持或停车，不发送穿越障碍的目标。

建议从右侧目标开始，每次向道路内部回退 0.2 m，直到找到安全 footprint 或耗尽可行区间。

### 9.5 横向连续性

禁止目标在帧间瞬移。至少限制：

- 单次 `d_target` 变化；
- 单位纵向距离的横向变化率；
- 横向曲率；
- 目标更新的最小位移和最小时间。

初始参数建议：

```yaml
max_lateral_step_m: 0.4
target_republish_distance_m: 0.5
target_republish_period_s: 1.0
```

在道路类型切换、进入/离开路口或边界置信度下降时，将横向目标平滑过渡，不能从 5 m 偏移瞬间跳回 OSM 线。

## 10. waypoint 语义与 Nav2 执行方式



### 10.1 OSM 锚点是进度门，不是横向目标

中间锚点 `i` 的通过条件改为路线弧长：

```text
s_robot >= s_anchor_i - progress_tolerance
```

同时要求机器人仍位于允许的路线走廊内，防止在平行道路上误判通过。

这比当前欧氏距离判断更符合“横向自由、纵向受约束”的需求。

### 10.2 不发送 90 m 的固定偏移批次

相机只能确认近距离道路边界，因此不能为整批远处 waypoint 生成横向位置。第一版建议：

- Campus Nav 保留完整原始路线和 cursor；
- 每次只向 Nav2 发送当前可靠视距内的 1 个动态目标，或最多 2～3 个短目标；
- 机器人沿 `s` 推进后重新估计边界并更新目标；
- 只有目标变化超过阈值或周期到达时才抢占 Nav2，避免高频取消重发。

最终目标、入口点和 off-network access leg 继续使用现有精确 `NavigateToPose` 流程，不进行道路边界吸附。

### 10.3 目标所有权

`RoutePlanner` 继续独占：

- `NavigateThroughPoses` / `NavigateToPose` action client；
- pause/cancel；
- 最终精确到达；
- heading lock 后重发；
- route cursor。

适配器只返回候选目标和状态，不直接发送 action。

## 11. 状态机

建议显式实现以下状态，而不是在回调中堆条件：

### `REFERENCE_ONLY`

- 当前路线不是机动车道路白名单；
- 不做道路右侧适配；
- 保持原有 footway/path/pedestrian 路线行为。



### `ACQUIRE_BOUNDARY`

- 进入机动车道路段；
- 尚未积累足够连续观测；
- 低速并收集边界；
- 不因单帧检测立即横移。



### `ALIGN_ROUTE_HEADING`

- 新路线方向与车头夹角超过阈值；
- 暂停动态目标与平移，调用 Nav2 `Spin` 原地朝向所选 OSM 支路；
- 对齐后丢弃转向前语义帧和拟合模型，重新连续采集边界；
- 解决目标位于车身后方时“看不到路线前方，因此永远不给 Nav2 目标”的死锁。



### `SEEK_RIGHT_EDGE`

- `road` mask 在路线右侧触及图像横向边缘，说明真实右边界尚未进入视野；
- 该包络只作为已确认路面的前沿，不更新物理路宽；
- 在 costmap 安全门控和单帧横向步长限制下，向该前沿内侧渐进；
- 真实 road/non-road 右边界进入画面后切换为 `TRACK_RIGHT`。



### `TRACK_RIGHT`

- 边界可信；
- 按右边界内缩位置生成目标；
- 正常推进路线进度。



### `JUNCTION_GUARD`

- 接近或离开路口；
- 限制边界候选到目标支路走廊；
- 降低横向变化率与速度。



### `HOLD_LAST`

- 短时丢失 mask、TF 或边界；
- 保持上一可靠横向模型；
- 只允许有限距离/时间继续行驶。



### `DEGRADED_STOP`

- 观测超时或边界不可信超过阈值；
- 不突然回到 OSM 左侧线；
- 停止或请求上层降级策略。



### `FINAL_APPROACH`

- 使用现有最终目标流程；
- 不再动态改变最终目标坐标。

关键原则：丢失道路时不能把目标立即恢复到原 OSM 线，否则机器人会突然向左横穿。

## 12. 现有梯度与固定 offset 的处理



### 12.1 固定 `road_right_offset_m`

动态适配启用后应设为 0，并最终删除对实际导航路线的固定偏移。它可保留为离线调试对照，但不能与动态目标同时生效。

### 12.2 当前图像空间横向梯度

当前语义层按 road mask 每行的图像左右生成梯度，隐含“相机正对道路”的假设。当车头朝路沿时，该梯度方向会错误。

正式系统有两种选择：

1. 第一阶段关闭该梯度，由动态目标负责横向位置；
2. 后续将梯度重写为地图中的路线坐标梯度，使用 `n_right(s)`，与动态目标共享同一方向定义。

不能同时保留“图像右侧”和“路线右侧”两套互相冲突的偏置。

## 15. 测试计划



### 15.1 纯数学单元测试

- 直线路线向东、向西、向北、向南时右法向正确；
- 路线反向后左右正确交换；
- 旋转车辆 yaw 但保持同一道路点集，估计的 `d_left/d_right` 不变；
- 车头朝路沿时，只要点被正确变换到 map，边界仍正确；
- OSM 线位于道路左侧、中心、右侧时，测得的物理右边界目标一致；
- 曲线路线切线连续，不在顶点翻转；
- 自交/平行路线在 `s_hint` 下不跳段。



### 15.2 边界估计单元测试

- 不同道路宽度；
- mask 内有车道线、斑马线、井盖孔洞；
- 少量远端错误 road 点；
- 两条平行道路同时可见；
- 十字路口和 T 字路口；
- 部分遮挡与低置信度；
- 道路只出现在画面左侧或右侧；
- 点云 NaN 和深度缺失。



### 15.3 时间行为测试

- 正常连续帧；
- 0.3 s 推理延迟；
- mask 掉帧；
- TF 暂时不可用；
- 时间戳倒退；
- 边界瞬时跳变；
- 从 `TRACK_RIGHT` 到 `HOLD_LAST` 再恢复；
- 长时间丢失进入 `DEGRADED_STOP`，且不向 OSM 左线猛转。



### 15.4 集成测试

- OSM 线在机动车道左侧；
- OSM 线在机动车道中心；
- 机动车道宽度逐渐变化；
- 机动车道接 footway，footway 不偏移；
- 正反方向分别行驶同一路段；
- 车头在绕障时短暂偏转 60～90 度；
- 进入路口并选择指定支路；
- 最终目标在道路外，通过 entry 精确进入；
- heading lock 导致 map/odom 调整后清图与重新获取边界。



### 15.5 验收指标

- 稳态目标距右边界误差不超过约 0.25 m；
- 目标单次横向跳变不超过配置上限；
- 路线进度 `s_robot` 单调推进，不被旧 waypoint 拉回；
- 语义失效时不产生向左横穿动作；
- 所有目标通过 footprint/terrain 安全校验；
- 边界计算平均耗时小于 50 ms；
- Nav2 目标更新频率不超过 1～2 Hz，且无持续抢占振荡。



## 16. 分阶段实施顺序



### 阶段 0：消除冲突

- 将固定 `road_right_offset_m` 设为 0；
- 暂停现有图像空间右侧梯度或将其设为不影响规划；
- 保留原始行为作为基线；
- 录制包含直路、弯道、路口、车头朝路沿的数据包。



### 阶段 1：路线坐标与边界离线验证

- 实现弧长路线、`s/d` 投影和 highway 元数据；
- 离线读取录包，输出 road 点和边界 marker；
- 不发送 Nav2 目标；
- 验证车辆 yaw 改变不会改变道路左右。



### 阶段 2：在线影子模式

- 在线同步语义帧和 TF；
- 发布动态目标和状态，但仍执行原路线；
- 比较动态目标、真实道路和 Nav2 plan；
- 接入现有 terrain/elevation 查询，记录相机边界与几何边界的一致性；
- 校准宽度、置信度、滤波和路口参数。



### 阶段 3：低速闭环

- 仅在指定测试路段启用；
- 限速；
- 一次只发送一个短视距目标；
- 保留人工急停；
- 验证 waypoint 不再向 OSM 左线牵引。



### 阶段 4：完整机动车道路段

- 扩展到全部白名单 highway；
- 接入路口保护、障碍否决和状态机；
- 恢复正常速度前完成正反向、宽窄路和遮挡测试。



### 阶段 5：后续人行道能力

- 加入 sidewalk 连通区域；
- 使用高程/地形确认无不可跨越路沿；
- 在右侧道路边界之外选择人行道中心；
- 再考虑 OSM A* 的 footway 优先权重。

### 可选阶段 6：原始雷达边界增强

- 仅在录包证明现有 terrain/elevation 不能满足边界安全判断后启动；
- 在路线坐标系内提取高度剖面和路沿，不建立第二套左右定义；
- Livox 短时累积必须做运动补偿；
- 以影子模式比较增强前后的边界召回率、误报率和计算开销；
- 达到收益门槛后才进入闭环，避免为少数场景长期维护一套高复杂度管线。



## 17. 主要风险与对应措施


| 风险                | 措施                                |
| ----------------- | --------------------------------- |
| 车头方向与道路方向不一致      | 左右只由有序路线切线定义                      |
| OSM 线本身横向误差大      | OSM 只定义 `s` 与方向，边界由语义点测量          |
| 相机没有看到路线前方        | 降低模型置信度，保持后停止，不猜边界                |
| 路口 mask 连成大片      | 路口保护区 + 目标支路走廊约束                  |
| road mask 被标线割裂   | 小尺度闭运算 + 连续区间 + 分位数边界             |
| 误分割出远端 road 点     | MAD/分位数/宽度检查/连续性检查                |
| 旧边界长期残留           | 明确 observation age 与 HOLD_LAST 上限 |
| 动态目标高频抖动          | 时间滤波、横向步长限制、目标更新门槛                |
| 目标落在障碍或路沿         | footprint + terrain veto，向道路内部搜索  |
| 固定 offset 与动态目标叠加 | 动态模式启用时强制固定 offset 为 0            |
| 图像右侧梯度方向错误        | 关闭或重写为路线坐标梯度                      |




## 18. 最终设计原则

1. OSM 负责拓扑，不负责精确横向位置；
2. 道路左右来自有序路线方向，不来自相机或车头方向；
3. 相机和车辆位姿负责把观测放到正确的时空坐标中；
4. 偏移量来自实际测得的道路边界，而不是固定米数；
5. 只对已观测的短视距目标做横向适配；
6. 中间锚点按纵向进度通过，最终目标保持精确；
7. 感知不可信时保持后停车，不能突然回拉到 OSM 线；
8. 语义目标必须经过障碍、地形和 footprint 的安全否决。
